启动流程

入口 cmd/server/main.go，启动顺序为：

  1. 进程硬化（engine.HardenProcess）—— 清 LD_PRELOAD 等危险环境变量
  2. 加载配置（config.Load）—— 环境变量 > 默认值
  3. 初始化 SQLite（store.Init）+ 种子数据（store.SeedIfEmpty）
  4. 初始化沙箱容器池（engine.InitSandboxPool）
  5. 启动即时调度器（scheduler.InitGlobal(engine.Run)）+ Cron 调度器
  6. 注册路由（api.NewRouter）→ 监听端口
  7. 优雅关闭：SIGINT/SIGTERM → 停调度器 → HTTP Shutdown → 关数据库

三、核心评测引擎功能

这是整个平台的心脏，也是最扎实、实现最完整的部分。engine.go:Run 是一个 8 步管线，全程不 panic（任何失败都标记 task=failed 兜底）。

3.1 意图识别路由（router.go）真实

单主 Agent 统管所有场景，不做 5 个独立场景 Agent（避免五份重复基建 + 数据隔离导致无法跨场景对比）。三级分类策略：

  1. 显式指定：用户直接传 scene 字段 → 置信度 100% 直接用
  2. 关键词匹配：每场景预设 7-9 个关键词，命中率 ≥ 60% 采用
  3. LLM 分类 fallback：低置信度时调 judge_models.main（需 Key）

5 个预置场景 → 4 种执行策略映射：

场景策略说明
agentsandbox_roundtable沙箱编译 + 圆桌合议（最完整）
modelapi_direct单判官，不走沙箱
competitor / prdtext_review圆桌评审
productmultimodal_review多模态评审

3.2 圆桌合议（roundtable.go）真实·设计精良

一个主导者 + 多个领域专家并发评审，区别于单判官的"一条规则调一次 LLM"。核心要点：

  • 专家从 judge_models 表动态加载（role 以 expert_ 开头），无数据回退预置 4 专家（安全/性能/架构/产品）
  • 也支持从 expert_groups 表加载可配置专家组（支持 agent/model/role 三类成员 + 内嵌 prompt + 引用 prompt_template + 权重 weight）
  • 各专家 goroutine 并发（sync.WaitGroup），每专家有 60s 超时保护不阻塞他人
  • 每专家只看自己维度的规则：metric 规则直接算（免费），llm 规则合并成 rubric 调一次 LLM
  • metric × 0.4 + llm × 0.6 加权（metric 确定性高但覆盖面窄）
  • 主导者按 weight 加权汇总 + 生成综合评语（自动找出最强/最弱维度）
  • 专家矛盾检测：同维度或跨维度评分差 > 30 分标记矛盾

3.3 双判官打分体系（judge.go + metric.go + scorer.go）真实

LLM 判官（judge.go）

规则 content 作 rubric，temperature=0 追求确定性，输出 {score, reason} JSON，正则兜底提取。

metric 判官（metric.go）

确定性校验器，不调 LLM。内置 checkNoInjection（检测 sprintf + SQL 拼接扣分，参数化 ? 加分）、checkNoSecretLeak（硬编码 sk-xxx 检测）、checkCompilable（括号配平 + 结构）、checkTestCoverage。

三轨分发（scorer.go）

metric / llm / manual 三种 scoring 方式，manual 为占位（阶段①不做人工 UI）。无 Key 时全套走启发式 mock 判官，保证 Demo 可演示。

3.4 钱包保护断路器（breaker.go）真实

解决"开发期 Agent 陷入无限内耗烧钱"问题。每题评测后检查三项上限：

上限项默认值说明
Token 上限10 万单次评测最大 token 消耗
Tool Calling 轮数30防止疯狂循环
费用上限$5按 GLM-4-flash $0.002/1K 估算

超限立即熔断 status=blown，已评测题仍写入报告（部分结果）。每题后通过 WebSocket 实时推送断路器状态。多 provider 定价表（GPT-4o / Claude / DeepSeek / GLM / Qwen / o1）硬编码在 estimateCost。

3.5 沙箱执行（sandbox.go + sandbox_pool.go）真实·双轨

Docker 容器池优先（Phase 2）→ 进程级沙箱回退（Phase 1）：

  • 进程级：临时目录 go build / python -m py_compile / node --check，支持 Go/Python/JS 三语言编译 + 测试 + Lint
  • Docker 池：网络隔离 --network none、资源限制、只读 FS、无特权
  • 采集硬指标：编译时延、编译成功/失败、测试通过率（解析 go test -v / pytest 输出）、Lint 错误数
  • Test-Gen 集成：将自动生成的测试代码注入沙箱与源码一同编译运行

3.6 反泄漏扫描（antileak.go）真实·纯启发式

每题评测后扫描，4 类检测，不调 LLM（免费确定）：

检测类型严重度说明
System Prompt 泄露critical回答含 "system prompt" / "系统指令" / "我被设定为" 等，isGenuineLeak 区分正常自我介绍 vs 真泄露
提示词注入high输入含 "忽略之前的指令" / "jailbreak" / "DAN 模式" 等 13 种越狱模式
踩额度攻击medium/high输入 > 10000 字 / 连续 5 次以上相同行刷屏
凭据泄露critical回答含 sk-xxx / api_key= / password= / 带密码的连接串，凭据脱敏后记入证据

3.7 混沌工程（chaos.go）真实

"线下林志玲，线上罗玉凤"——主动注入故障测鲁棒性。4 种注入（仅对前 2 题注入，避免成本爆炸）：

  1. 弱网延迟：注入"API 超时 5000ms"提示，检测是否提到重试/降级
  2. 脏数据：注入缺右括号的 JSON，检测是否识别格式错误
  3. 越狱对抗：尝试让 Agent 忽略安全约束，拒绝 = 95 分，泄露 System Prompt = 10 分
  4. 资源耗尽：模拟磁盘满 / 内存不足 / 配额耗尽，检测是否提降级方案

每次注入记录到 permissions 表（chaos_injected=1），鲁棒性分聚合进报告。

3.8 RAG 规则检索（rag.go）真实 embedding 占位

规则多了不爆 token，每题只检索 top-K 相关规则：

  • 检索 / 相似度排序 / 关系边查找链路完整工作
  • 但 embedding 是 hashing-trick 占位：FNV-1a 哈希把词映射到 128 维固定位置 + L2 归一化，不是真实 embedding 模型（代码注释明确"生产环境应替换"）
  • 支持沿 rule_relations 关系边拉关联规则（知识图谱）
  • 可持久化到 rag_embeddings 表

3.9 异常归因闭环（attribution.go）真实·含自动反哺

评测有 Bad Case 时后台异步分析根因（不阻塞主流程）：

  • 4 类根因分类：prompt_compliance（指令遵循）/ context_loss（上下文丢失）/ tool_failure（工具失败）/ model_limit（模型上限）
  • 启发式归因（无 Key 时）+ LLM 归因
  • 自动闭环反哺：置信度 ≥ 0.7 时，自动把修正建议写回 prompt_templates 表（创建新模板或新版本），实现"评测 → 暴露 Bug → 归因 → 提示词进化"
  • 高置信度（≥ 0.8）建议通过日志提示用户采纳

4.7 中间件与问题

中间件：requestID + CORS（硬编码 localhost:5173）。无任何鉴权：所有端点裸奔，终端执行/代理控制/API Key 写入均无保护。
requestID 生成 bug：generateShortID() 确定性（make([]byte,12) 零初始化 + 异或固定），所有请求同一 ID，追踪失效。
正面确认：所有动态 SQL 均用 ? 参数化，未发现 SQL 注入。也没有空 handler 或纯 TODO 占位函数。

六、协议逆向与调度子系统

6.1 MITM 代理（internal/proxy/）真实 有 bug

  • HTTP 代理（proxy.go）：反向代理 + request/response 捕获 + 凭证提取（Bearer/x-api-key/sk-/Cookie）+ 脱敏（前4后4）+ ReplaySession + ConvertSessionToTask
  • HTTPS MITM（proxy_tls.go）：手写解析 TLS ClientHello 提取 SNI → 动态签发证书 → 伪服务器握手 → 明文读 HTTP → 真实客户端转发。HTTP/1.1 keep-alive 支持，body 脱敏
  • CA 管理（ca.go）：RSA 2048 自签 CA（10 年），leaf 证书按域名缓存（24h），各平台安装指引
  • 环境变量重定向（redirector.go）：对标 claude-code-router，生成 ANTHROPIC_BASE_URL / OPENAI_BASE_URL 注入脚本。诚实降级：MRD 的激进灰色能力（TLS 指纹伪造 / IPC 劫持 / 配置解密）全部 return ErrNotImplemented
已知 bug：HTTP 代理 session 分组逻辑错误（所有请求进同一 session）；HTTP 路径不脱敏但 HTTPS 脱敏，两条路径不一致；存在死代码（旧 peekSNI/handleConnection 未删）。

6.2 调度器（internal/scheduler/）真实

即时调度（scheduler.go + global.go）

channel-based Worker Pool（默认 3 worker，buffered channel 容量 100），单任务超时 300s + 重试 2 次，running map 去重。RunDirect 作为队列满时的降级保底。

优先级字段是摆设：Task.Priority 字段存在，Submit 也接收 priority，但 worker 从单一 channel 取任务，channel 是 FIFO，优先级完全没有被使用。

Cron 调度（cron.go + global_cron.go）

自研简化 Cron（不依赖外部库），30s 轮询检查，持久化到 cron_jobs 表。解析极度残缺：只处理 5 字段的前两位（minute/hour），日/月/周字段被忽略；不支持范围（1-5）、列表（1,3,5）。

6.3 SDK 接入（internal/sdk/）真实 包路径混乱

  • PlatformClient：RegisterAgent / ListAgents / SubmitTask / GetTask / WaitForTask（2s 轮询 10min 超时）/ ListRuleSets / ListQuestions
  • EvalHandler：Agent 侧 HTTP Handler，平台 POST /eval 调 Agent
  • MCPServerHandler：MCP 协议适配（ListTools + call_tool）
  • CLI（eval-cli）：register / submit / status / list 四类命令，平台地址和 key 从环境变量读
  • mock-agent 示例：完整端到端演示（启动 :9090 Agent → 注册自己 → 提交评测 → 等结果），按 prompt 关键词返回不同 mock Go 代码
包路径问题：internal/sdk 和 pkg/sdk 维护了两份副本，CLI/示例 import pkg/sdk，README 写 internal/sdk，矛盾。需确认哪份是 source of truth。

十、总体结论

这是一个完成度相当高、架构清晰、核心功能真实落地的 AI 评测平台。它不是 PPT 项目或占位壳——编译产物存在、数据库在运行、187 个测试、145 个 API 端点、44 张表、18 个前端页面全部对接真实后端。

最扎实的部分是评测引擎（圆桌合议 + 沙箱 + 断路器 + 归因闭环）和 harness 六层能力（ReAct + Tools + MCP + Skills + Subagents + Hooks），这两块是真正的工程价值所在。最薄弱的部分是六大扩展方向（Arena/Finetune/Workflow 有真实 bug）和安全（无鉴权 + API Key 明文 + 加密默认 key）。

项目对自己的能力边界很诚实——docs/ARCHITECTURE.md 主动校准了对 claw-code 和 claude-code-router 的误读，把法律灰色能力降级为预留接口。这种"能让系统真正可用、可维护、可演示的做；灰色、高成本、低实用性的降级"的工程判断，是成熟的表现。
